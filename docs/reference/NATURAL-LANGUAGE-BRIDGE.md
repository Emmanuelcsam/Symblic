Symblic's central idea is to program with small, explicit statements whose results can be composed. An LLM can construct a result, a program fragment or a logical derivation. A separate checker determines what that particular result establishes. The model remains a computational backend; writing every domain algorithm into the kernel is not required.

The original stronger premise needs one revision: a perfectly worded instruction does not guarantee that a model will execute it perfectly or repeat the same answer. Specificity reduces some ambiguity and makes errors easier to detect. Reliability comes from the combination of specification, bounded construction, independent checking, evidence and explicit failure behavior.

## Choose the right execution lane

| Lane | Model or human supplies | Checker establishes | What remains open |
|---|---|---|---|
| Deterministic computation | An expression and its input values | The result of the supported computation under the pinned implementation | Whether the inputs and modeled relationship describe the task or world |
| Proof-carrying construction | A derivation of the caller's declared proposition | That the supplied proof follows the supported inference rules from its declared premises | Premise truth, consistency, translation adequacy and existence of a proof within the budget |
| Source-witnessed interpretation | Candidate source spans and structured values | Exact source identity and the declared field, coverage or finite-catalog relationship | General paraphrase entailment, source credibility and undeclared qualifications |
| Empirical judgment | A classification, plan, summary or other proposal | Its output type and whichever particular tests actually ran | Unchecked meaning, generalization and real-world success |

These lanes compose. A model may find a proof while a deterministic checker validates it. It may construct code while an isolated test harness exercises that code. It may identify a source field while the checker validates its exact label, scope, unit and value witness. Use ordinary computation directly when it is already the simplest solution; keep the construction lane when finding a solution is the work the model should perform.

Proof production and proof checking are established separate responsibilities in theorem-proving systems. The reform applies that separation to model calls without claiming that an LLM's explanation is automatically a proof. [Lean's trusted kernel account](https://lean-lang.org/doc/reference/latest/Elaboration-and-Compilation/)

## Start with the statement and its failure cases

For each step, write down:

1. The inputs and their origins: operator premise, adopted assumption, source report, observation, model proposal or derived result.
2. The intended output, including unknown or contested outcomes where the domain needs them.
3. What would establish acceptance: a derivation, an exact witness, an executable predicate, finite examples, or a combination.
4. Counterexamples the contract must reject, including a plausible answer about the wrong entity, an empty answer, a lost exception and an answer copied from another source revision.
5. Which later steps depend on the result, the permitted effects, and the call, context and execution budgets.

A source can be authoritative for the task without becoming infallible. An adopted assumption authorizes reasoning under it; adoption does not turn it into an observation. A passed arithmetic check must retain the origin of the quantities it used.

## Exact computation remains available

This complete example needs no model or external capability.

<!-- symblic-example: exact-tip; mode=kernel; expected=done -->
```symblic
program ExactTip.
let bill = 45.60.
let tip = bill * 15 / 100.
assert tip = 6.84.
show tip.
```

The equality concerns an exact rational calculation. It does not establish that the bill is genuine, that 15% is the intended policy, or that a measured quantity has no uncertainty. Measurements need their units, interval or tolerance, source and applicable time, independently of the arithmetic representation.

## Human statements can be formal propositions

The implemented reform fragment is **intuitionistic propositional logic**. Human-readable atoms are JSON-quoted text, combined with `and`, `or`, `implies`, `not` and parentheses. For example, `"The switch is on" implies "The circuit is energized"` has explicit formal structure. The checker treats each quoted statement as an opaque proposition; it does not infer electrical facts from the English words.

This complete example supplies a proof of a proposition implying itself. It checks the proof without searching for one.

<!-- symblic-example: identity-proof; mode=kernel; expected=done -->
```symblic
program IdentityProof.
use profile=verified.
let p = proof_parse("\"The switch is on\"").
let goal = proof_parse("\"The switch is on\" implies \"The switch is on\"").
let certificate = {version: 1, proof: ["implies_intro", "h", p, ["hypothesis", "h"]]}.
let checked = proof_check({:}, goal, certificate).
assert checked.valid.
assert len(checked.used_premises) = 0.
show checked.
```

The term introduces an assumption, uses that assumption and discharges it. The premise record is empty (`{:}`); `{}` remains an empty set. The receipt confirms no premises were used. Other supported rules combine or eliminate conjunctions, disjunctions and implications. [PROOF-TERMS](PROOF-TERMS.md) defines the complete grammar, lexical scope, bounds and receipt fields.

`"Every person is mortal"` is one opaque atom, not a quantified formula. The separate finite-domain frontend now compiles quantified formulas over caller-declared finite domains into ground propositions and bounded conjunctions/disjunctions. Its isolated compiler/API checks exercise that finite contract. It is not unrestricted first-order logic, induction or an English theorem interpreter. The Logic interface exposes the selected fragment and optional finite domains; its installed release is recorded in [REFORM-3](REFORM-3.md).

## Let a model construct the derivation

The following complete program holds the premises and goal outside the candidate's control. The model supplies only the certificate. The checker does not insert missing premises or search for a derivation.

<!-- symblic-example: constructed-proof; mode=fake-proof; expected=done -->
```symblic
program ConstructedProof.
use profile=verified.
let p = proof_parse("\"Socrates is human\"").
let goal = proof_parse("\"Socrates is mortal\"").
let premises = {human: p, rule: ["implies", p, goal]}.
ask certificate: Any "Construct a proof term of goal from premises. Return only version and proof."
  from premises, goal with effort=low, route=escalate, retries=1
let checked = proof_check(premises, goal, certificate).
ensure checked.valid else retry.
show checked.
```

For documentation verification, an injected fake applicator supplies the modus-ponens certificate from `tests/adapters/test_symblic_proof_run.py`; no real model is called. That verifies the execution path, not a model's ability to find the proof. Actual model performance requires a separately recorded experiment.

A successful result means that the conclusion follows from the supplied premises in the implemented calculus. It does not establish that those premises are true. The proof calculus includes elimination of falsity; inconsistent premises can therefore support arbitrary conclusions. The separate epistemic policy preserves disputes and can refuse contested premises for operational use. That policy does not silently change the formal calculus into a paraconsistent logic.

A timeout or rejected certificate means that this attempt did not establish the goal. It is not a proof that the goal is false or unprovable.

Generating implications and their supporting proofs over specified natural-language theories is also an existing research task. ProofWriter provides a relevant comparison for learned construction; its results do not guarantee correct proofs for arbitrary English or for Symblic's fragment. [ProofWriter](https://arxiv.org/abs/2012.13048)

## Types constrain representation; witnesses constrain more

A type can require a Boolean, a member of a finite choice, or a record with particular fields. Provider paths differ: some support grammar/schema-constrained generation, while other replies must be parsed and validated after generation. The runtime can reject or repair malformed replies. It cannot promise that every provider is physically incapable of producing invalid output.

The `verified` reform profile rejects undeclared coercions such as discarding an extra warning field or treating a fuzzy enum spelling as its canonical value. Declared rounding and set semantics remain available. The compatibility profile retains older transformations with receipts describing what changed. A type conversion must not silently erase a qualification and then present the remaining number as fully verified.

Even perfectly typed data can be wrong:

| Request | Insufficient check | Stronger declared contract |
|---|---|---|
| Extract the invoice total | The quote contains the number `3` | Exact total-label anchor, selected invoice/entity region, value position and declared unit/currency; refuse ambiguous repeated labels |
| List the metals in a passage | Every returned item occurs in the text; `[]` passes | Per-item witnesses plus required finite catalog IDs, or an explicit report that completeness is unknown |
| Summarize an article faithfully | The answer has at most 40 words | Exact extractive spans plus required exception/coverage IDs; a free paraphrase remains a proposal |
| Establish a logical conclusion | The output equals the requested conclusion | A checked derivation from caller-pinned premises |
| Construct a component | The code parses | Independent behavior tests, composition checks and failure cases, with untested behavior visible |

The witnessed field contract is deliberately a supported literal relationship, not a hidden general-purpose semantic parser. It handles declared aliases; it does not invent them. It refuses unsupported layouts, mismatched currency and unmodeled negation rather than claiming that quotation alone establishes the referent. Existing free-form routines remain useful when their weaker assurance is acceptable.

## Compose evidence as well as values

Every accepted edge needs its value plus the evidence needed by its consumer. The reform envelope records exact content, origin, revision, dependency pins, checked predicates and receipt IDs. Unknown, contested, refuted and conditional states remain distinct.

For example, a model reports an invoice amount of 3, and the kernel correctly computes 10% tax as 0.3. The arithmetic result is still conditional on that model-reported amount. It is not a newly observed invoice total. If the source revision changes or the assumption is withdrawn, downstream support becomes stale and must be recomputed or explicitly re-established.

Context follows the same rule. Required selected values must fit with the statement, system instructions, schema, definitions, examples and feedback. Ancestor identities and support conditions are retained as lineage metadata, without automatically expanding forgotten or unrequested ancestor raw values. If they do not fit, construction fails visibly. Optional context may be omitted with named IDs, hashes and reasons. A high numerical weight cannot make an omitted premise safe, and a short capsule does not prove that all relevant meaning has survived.

## Queries, obligations and effects are different operations

`1 = 2.` evaluates a Boolean query; it does not assert that the Boolean must be true. Use `assert 1 = 2.` for a failing obligation. The reform profiles diagnose bare Boolean queries and prevent an unrecognized instruction such as `asertt false.` from becoming an accidental model request in explicit/verified programs. Legacy prose remains available under its compatibility contract.

A pure function must remain pure in the verified profile. Model calls and effectful routines belong in explicit execution steps. Existing capabilities, Datalog, exact adapters, code generation and legacy programs are preserved; stronger contracts are additive and migration is explicit.

An external action requires the existing host capability, authority and durable-effect rules. The runner already forbids an action or delegation inside a retry window that could replay it. Recorded unknown outcomes require recovery; memory rollback cannot unsend an email. the host executor's selected full/guarded policy remains authoritative. A checked Boolean can still be attacker-influenced, so influence labels and effect policy must survive the check.

## From a pipeline to an agent network

A network can contain model constructors, deterministic functions, proof/source checkers, observations and bounded feedback. Each node needs an input/output contract and state transition; each edge needs a schema, evidence requirements and dependency identity. Routing, iteration limits, cancellation, replay and external effects must have explicit semantics.

This is a useful level of composition without claiming that an LLM is literally a boosted tree or that API calls have become differentiable neurons. Transformer computation uses attention and learned transformations. An agent graph needs a separately specified objective and update rule before it can be called a learned network. [Attention Is All You Need](https://arxiv.org/abs/1706.03762)

The practical promise is testable: small construction tasks may be easier to solve and verify; accepted results can be reused with their conditions; failures can be localized and repaired. Whether that beats direct prompting or ordinary code on a whole project depends on source fidelity, specification effort, checker strength, routing overhead and measured end-to-end outcomes.
