## Executive Summary

This document proposes how **Symblic** could be developed and run on **High-Performance Computing (HPC)** systems.

It addresses four design questions:
1. **HPC Execution:** what distributed inference, larger test-time search, parallel Datalog and numerical solver backends would involve, set against what Symblic has today:
   - model calls placed on the original host's few worker nodes;
   - checked search over at most 25 candidates per round;
   - a single-threaded Datalog engine capped at 200 000 facts;
   - an exact rational quadratic solver limited to 32 unknowns.
2. **HPC Training & RLVR:** whether reinforcement learning with verifiable rewards (RLVR) could train an autoformalizer and a schema reader with the kernel's verdicts as the reward. Nothing has been trained. The kernel's verdict is deterministic by design, and its results on a fixed corpus matched across 27 tested profiles (Part 3). But it rewards conformance to the predicate as written, so a policy can game it wherever the predicate is weaker than the task.
3. **Training Risks & Failure Modes:** how known failure modes of fine-tuning and RL could make a trained component worse (reward hacking, catastrophic forgetting, loss of calibration), and how each would show up in Symblic.
4. **The Shippable Product Roadmap:** proposals for packaging and tooling, none built as proposed, next to what exists: `tools/symblic`, the page's editor and Preview, and run locks with replay.

### 1.1 Path A: HPC Execution & Distributed Scaling

Symblic has not been deployed on an HPC cluster (InfiniBand, a SLURM scheduler, multi-GPU nodes), and no Symblic code targets one. What existed on the original host was placement on its small fleet of worker nodes:
- A run started from the page or API is a systemd unit on the host that only orchestrates: `a systemd slice for work`, MemoryMax 600M, CPUQuota 50%, nice 10 (SPEC.md:488-489). `tools/symblic run` runs in the terminal that started it, under nice 10 (`tools/symblic:5-6, 17`).
- A CLI or Ollama call without `@node` goes to a worker node through the fleet runner's admitted launch path; the host is used only when named (`@host`). The path applies the power fence and capacity caps, and for Ollama the memory gate (SPEC.md:400-404; `symblic/providers/applicators.py:1-18`).

The four proposals, with their status:

1. **Distributed Multi-Node Inference (proposal, not built):**
   vLLM and SGLang can serve large open-weight models across multi-GPU nodes with tensor and pipeline parallelism behind one API endpoint. Examples are Llama-3.1-405B, DeepSeek-R1-671B and Qwen2.5-72B.
   - **No applicator for it:** Symblic's engines are the agent CLIs, Ollama through the fleet runner, the browser daemon, a host model service, Councils and the kernel (`symblic/kernel/language.py:4880`; `symblic/providers/applicators.py:1-18`).
   - **How one would be added:** as a new applicator on an admitted launch path, never as a direct call (`symblic/providers/applicators.py:10-11`; RESEARCH-ADOPTION.md:122).
   - **Models in the record:** the recorded Tetris build used three small local models, qwen3:4b-instruct, phi4-mini and gemma3:4b, in Ollama on CPU-only worker nodes (SPEC-SHEETS.md:159-160).
   - **Replay:** a served model would not change it, because replay serves recorded replies. Fresh samples from vLLM are not guaranteed to be reproducible by default (PRIOR-ART.md:525-527).
2. **Test-Time Scaling (rejected as proposed; smaller checked sampling exists):**
   - **Votes:** `votes` is capped at 25; a larger value is clamped to 25 (`symblic/kernel/run.py:1019`).
   - **`effort=ultra`:** 5 votes, then a second round in which each applicator sees up to 6 anonymised candidates (SPEC.md:257; `symblic/kernel/language.py:4932`).
   - **Checked best-of-N** exists as `route=search` (2.4): up to 25 candidates per round and up to 20 rounds. Each candidate is repaired against its own failures, and the pass with the fewest attempts is selected deterministically (SPEC.md:94-102; `symblic/kernel/run.py:340-341`).
   - **Call limits:** `parallel` (1–16, default 4; the page API accepts 1–8) sets the size of each worker pool, so one round of an ask runs at most that many calls at once. A `for each` ask runs up to `parallel` items at once and each item's vote opens its own pool, so Symblic sets no run-wide cap on concurrent calls; each CLI or Ollama call waits for room under the fleet runner's capacity rule before it launches (`symblic/kernel/run.py:47, 419, 995-997, 1357-1358`; `integration/host/symblic_engine.py:218`; SPEC.md:403-404). `max_calls` limits a run's fresh calls to 2 000 by default; the CLI accepts any value and the page API up to 10 000 (SPEC.md:416-417; `symblic/kernel/run.py:46, 393`; `tools/symblic:44`; `integration/host/symblic_engine.py:218`).
   - **Rejected:** raising votes to 100–1,000 and adding sequential Monte Carlo (REVIEW-2.3.md:194). More samples from the same models are correlated repeats, not independent readings. SMC needs an explicit proposal, a target or factor model, weights and resampling (RESEARCH-ADOPTION.md:121: "More votes are not SMC"), and one whole-answer call supplies none of these. Adaptive sampling (`ahead`, first-to-ahead-by-k) and checked escalation (`route=escalate`) already exist (REVIEW-2.3.md:194; SPEC.md:259, 273).
   - PPDL (Mandel, Baudart, Vaziri and Hirzel 2026; [PRIOR-ART.md](PRIOR-ART.md)) is a language-level example of SMC over LLM flows.
3. **Deterministic Kernel Workloads (deferred):**
   - **Parallel Datalog:** deferred, because no measured workload needs millions of facts (REVIEW-2.3.md:195).
     - Symblic's Datalog is a single-threaded, in-process Python evaluator with stratified, closed-world negation. One run holds at most 200 000 facts (a fixed limit) and, by default, 200 000 kernel steps; an embedding host can change the step budget (`max_steps`) (`symblic/kernel/language.py:47, 51, 3559-3560, 3624-3625`; `symblic/kernel/run.py:372`; SPEC.md:416, 452-454).
     - A Soufflé backend would be a second implementation of those semantics, and it would need its own conformance tests against the kernel.
   - **Linear Solvers:** deferred, because floating-point BLAS/LAPACK or PETSc routines would break the exact-arithmetic contract (REVIEW-2.3.md:195). The solver this item refers to is `symblic.adapters.variational` (adapter version 1, added in 2.2).
     - **What it does:** it minimises an explicitly supplied rational SPD quadratic ½xᵀAx − bᵀx with at most 32 unknowns, by an exact LDLᵀ factorisation. `quadratic_verify` checks its witness independently (`symblic/adapters/variational.py:1-24`; [VARIATIONAL.md](VARIATIONAL.md)).
     - **The mathematics:** minimising an SPD quadratic is one linear solve, Ax = b, with a unique minimiser (Boyd and Vandenberghe 2004, *Convex Optimization*, Example 4.5).
     - **What it is not:** it assembles no PDE and is not connected to `solve=true`. It does no spatial or physical optimisation beyond the matrix it is given.
     - **A floating-point backend** would be a different adapter, with its own precision, version and bounded-resource contract (RESEARCH-ADOPTION.md:122).
4. **SLURM Job Scheduler Directives (rejected):**
   Rejected in REVIEW-2.3.md:193. Placement belongs to the host, and scheduler options in program text would tie a program, its lock and its replay to one site. The proposed line is not valid Symblic (`symblic/kernel/language.py:4880, 4902-4904`):
   - `check` refuses `nodes` as an unknown ask option;
   - `Report` is not a defined type;
   - `hpc` is not an applicator engine; `check` does not test applicator names, but a run refuses it.
   ```symblic
   # proposed and rejected; refused by check
   ask result: Report "Analyze fleet telemetry" with by="hpc:slurm", nodes=4, gpus=8
   ```
   What exists is an applicator spec with an optional node, `engine[:model][@node][+effort][*weight]` (SPEC.md:394); without `@node`, the host picks a worker node (SPEC.md:400-404). For example, with a named node:
   ```symblic
   given telemetry: Text.
   ask summary: Text up to 80 words "Summarise the fleet telemetry." from telemetry with by="ollama:qwen3:4b-instruct@node-a".
   ```

### 1.2 Path B: HPC Training & Reinforcement Learning with Verifiable Rewards (RLVR)

Nothing in this section exists. Symblic has no model-training code, training dataset or trained model. RLVR training is recorded as deferred: "a large, compute-heavy research project with no baseline measurement" (REVIEW-2.3.md:196).

#### What Should (and Should Not) Be Trained
- **The Deterministic Kernel is not trained:**
  - Exact rational arithmetic, Datalog fixpoints and the LDLᵀ solver are exact algorithms. `0.1 + 0.2 = 0.3` is true, because `0.1` is 1/10 (SPEC.md:165; `tests/kernel/test_symblic.py:126-127`).
  - A trained network computing them would replace an exact result with an approximate one that can be wrong, and there is nothing to gain.
- **The Specialized Symblic Models (proposal):** train a dedicated model (e.g. 7B, 14B or 32B) for three roles. Today untrained models fill the first two roles, and the kernel checks what they produce.
  1. **The Autoformalizer:** translating a plain-English request into a `.sym` program that passes `check`.
     - **What `check` decides:** syntax, names, types, capabilities and information flow. It does not decide whether the program does what was meant (`host_executor_plan.py:3-4`; SPEC.md:131-135).
     - **the host executor's planner:** an ordinary model writes the program and `symblic.kernel.effects.check` decides whether it may run. Errors go back to the planner once (`host_executor_plan.py:1-12`).
     - **The Interpreter page:** it helps the operator refine a request into explicit requirements and questions, keeps a model's proposals labelled as proposals, and then compiles the request to checked Symblic (SPEC.md:131-135; INTERPRETER.md:1-25).
     - **Spec sheets:** they compile a strict Markdown description into a program with no model at all (SPEC.md:106-109).
  2. **The Schema Contract Reader:** fine-tuning an applicator to return answers that pass the type checks on the first attempt.
     - **Schemas are already enforced:** the answer's JSON Schema goes to each CLI's structured-output flag, and for Ollama it becomes `format`, which constrains decoding to the schema (`symblic/providers/applicators.py:3-10`).
     - **The kernel re-checks every reply** against the declared type; lengths and ranges are enforced by the kernel independently of provider schema support (SPEC.md:200-205).
     - **`Code` answers** (2.4) send no JSON schema at all (SPEC.md:86-89).
  3. **RLVR / GRPO:** using the kernel's verdicts on `ensure` and `assert` as the reward.
     - **Verifiable, in the RLVR sense:** for a given program, answer and kernel identity, the verdict is designed to be deterministic ("intended to give equal results", SPEC.md:5-7), and a fixed corpus gave the same results on 27 tested profiles (RESULTS.md:132-140). The term RLVR comes from the Tülu 3 report (Lambert et al. 2024); GRPO comes from Shao et al. 2024.
     - **Gameable:** a passing check establishes conformance to the encoded predicate, and "A weak, mistaken or circular predicate can accept a wrong answer" (SPEC.md:337-338). §1.3 gives the standard example.

#### Would Training Make Significant Improvements?
Unknown: nothing has been measured, and the figures in the earlier draft had no source.
- **Speed & Latency:** the earlier draft said a fine-tuned 7B/14B model with ">98% first-pass schema compliance" would eliminate retry loops. That rested on no measurement.
  - Retries follow failed checks as well as invalid replies (SPEC.md:264), and schema-valid replies can be wrong.
  - In the from-scratch Tetris validation, every unit's accepted answer passed on its first attempt. That run's cost was inference time: 141 calls and 8.7 model-hours on CPU (SPEC-SHEETS.md:170-174).
- **Accuracy on Formal Tasks:** unmeasured.
  - In two six-case pilots, typed (schema-constrained) answers alone gave no accuracy gain over natural prompts (RESULTS.md:155-194: "Schema alone showed no gain on these instances").
  - A trained model's programs must pass `check` and also do what was asked. Measuring that needs a held-out, independently labelled task set under matched budgets (RESEARCH-ADOPTION.md:119-120), and none exists.
  - Checked execution can improve a system's accepted results while leaving the model's own accuracy unchanged (RESEARCH-ADOPTION.md:119).

### 1.3 Critical Failure Modes: Can Training Make Symblic Worse?

**Yes, it can.** Fine-tuning and RL have three documented failure modes that would apply to a trained Symblic component. None has been observed here, because nothing has been trained.

1. **Reward Hacking / Goodhart's Law:**
   A policy rewarded only for passing `ensure` conditions can learn shortcuts that satisfy the predicate without doing the task. This is reward hacking (Amodei et al. 2016), a case of Goodhart's law.
   * *The Counterexample:*
     - **The weakness is real:** the extraction `{quantity: 1, unit_price: 1, total: 1}` satisfies `quantity × unit_price = total` for any invoice, including one that says 3 laptops at $800 each (SPEC.md:559-561). RESULTS.md:59-64 lists it among the counterexamples executed, with fake replies and no model calls, in the review of the AGY study documents.
     - **It is not a training result**, and the earlier claim that it came from "our test suite" was wrong as stated. The closest test is an Interpreter case: a reading "one laptop at one dollar" of "3 laptops at $800 each" is recorded as compatible, with `semantic_correctness: not_established` (`tests/intent/test_symblic_intent.py:344-354`).
     - **Symblic 2.3's defence is source grounding.** `text.quoted_number_in` makes the model return the span that states each number. That establishes that the number is written in the passage, not which thing it describes (SPEC.md:557-563).
     - **For training,** a policy trained against `Q × P = T` alone could learn the shortcut. A reward should include grounding checks, and it should be measured on held-out tasks (RESEARCH-ADOPTION.md:120).
2. **Catastrophic Forgetting of Linguistic Nuance:**
   Fine-tuning on one task can degrade abilities learned earlier (catastrophic interference: McCloskey and Cohen 1989; Kirkpatrick et al. 2017). Heavy fine-tuning on Symblic syntax could therefore weaken the reading comprehension and world knowledge an applicator is used for. Whether it would is unmeasured; detecting it needs held-out reading tasks scored before and after training.
3. **Confidence Distortion & Calibration Loss:**
   Post-training can make a model less calibrated. The GPT-4 Technical Report shows the post-trained model less calibrated than the pre-trained one on an MMLU subset (OpenAI 2023).
   - **Votes would not change:** Symblic's consensus reads no model-reported confidence. Answers are grouped by fingerprint and weighted by the applicator weight the author set, and the reported entropy is computed over the answers (SPEC.md:283-289).
   - **The harm that remains:** a model that is consistently wrong gives samples that agree with each other. They raise the agreement share without adding evidence.
   - **Two existing rules limit what that agreement can claim.** Agreement is never treated as correctness (SPEC.md:336-337). And `families=N` counts models by the maker of their base weights (and a distill's teacher), so a fine-tune adds no family beyond its base when its lineage is known (SPEC.md:299-308).

#### Training Parameters & Dataset Composition (untested proposal)
No dataset exists, and no experiment chose any of these values. RESEARCH-ADOPTION.md:120 sets three preconditions:
- an independently labelled dataset with adversarial negatives and hidden tests;
- training only in an isolated, admitted experiment;
- comparison against the same untrained checkpoint.

The proposal:
- **Base Models:** pre-trained base weights (e.g. Qwen2.5-14B or Llama-3.1-8B base models).
- **Dataset Composition (none exists):**
  1. 100,000+ triples `(Unstructured Document, Typed Schema, Verified Inhabitant)`. Here "verified" can only mean "passes the kernel's checks"; correctness needs independent labels.
  2. 50,000+ pairs `(Plain English Intent, .sym program that passes check)`, with task-level labels for whether each program does what was asked.
  3. Negative trajectories: failed extractions paired with the kernel's rejection message and the repaired answer. Symblic's run records keep most of this. `calls.jsonl` keeps every model call's reply, rejected or accepted; `retry` rows in `trace.jsonl` mark each failed check by its line, with its `because` text or error when there is one; and `report.diagnoses` lists the rejected answers when a check runs out of retries. The feedback text itself is not stored: it is part of the prompt, which enters each call's key only as a hash, so a dataset would rebuild it from the program and these records (SPEC.md:319-335, 480-483; `symblic/kernel/run.py:551-560, 1538-1545`).
- **Hyperparameters (unvalidated starting guesses):** learning rate $\sim 1 \times 10^{-5}$ for SFT and $1 \times 10^{-6}$ for RL/GRPO, with a KL-divergence penalty ($\beta = 0.05\text{--}0.1$). A KL penalty limits how far the policy moves from the reference model. It does not by itself preserve reading ability, which would have to be measured.

## Part 3: The Shippable Product Roadmap

None of these five items has been built as proposed; each says what exists now. RESEARCH-ADOPTION.md:123 sets the bar for a release:
- a supported portable kernel subset;
- reproducible builds;
- conformance fixtures;
- versioned module formats;
- documentation and a threat model.

It adds: "A package installer or demo alone is not a language release or a novelty result."

1. **Single Standalone Native Binary (not built):**
   The proposal is to package the kernel, parser, Datalog engine and variational solver into one native binary (Rust, or compiled C/Python).
   - **What exists** is `tools/symblic`, a shell wrapper around Python with `check`, `preview`, `run`, `replay`, `test`, `certify`, `lib`, `doc`, `paper` and `lock` (`tools/symblic:1-20`).
   - **Dependencies:** the kernel needs no third-party package. `symblic/kernel/language.py`, the first-party modules it loads at import (`symblic/kernel/language.py:4983-5025`) and its adapters import only Python's standard library and other Symblic modules (`symblic/kernel/language.py:26-36`). The system as a whole is not zero-dependency. Model applicators reach the dashboard hub and the fleet runner (`symblic/providers/applicators.py:1-18, 34`). The JavaScript adapter needs Node, and the adapter and Node versions are part of the kernel identity (`symblic/js/check.py:22-24, 92-94`; SPEC.md:90-92).
   - **No installer exists.** No code or configuration in the repository refers to `symblic.dev`; the domain and the earlier draft's `curl ... | sh` line occur only in assistant-written documents. The line has been removed here.
2. **VS Code Extension & Language Server Protocol (LSP) (not built):**
   What exists:
   - **`tools/symblic check`** reports syntax errors, unknown names and types, and builtin-name collisions (`let count = 1.` gives "count is a builtin function name", `symblic/kernel/language.py:4108-4114`). It also reports the warnings `SYM_VACUOUS` and `SYM_SAME_KEY` and a predictability score per ask (SPEC.md:340-347, 584-589).
   - **The page's editor** sends the program to `check` 450 ms after each edit and marks errors and warnings in the gutter (`web/studio/symblic-page.js:165-173, 297, 381-385`). This is the page's own editor calling the operator-only API (SPEC.md:526-529), not an editor extension or a language server.
   - **The page's Preview** (/automation-studio/symblic.html) shows the system line, the exact capsule and the answer schema for the first ask (`web/studio/symblic-page.js:482-495`; SPEC.md:533-534). It reports no token count; the context budget is in characters, default 12,000 (SPEC.md:247).
3. **Pluggable Multi-Backend Adapters (`symblic.toml`) (not built):**
   No configuration file exists. Applicators are named in the program (`engine[:model][@node][+effort][*weight]`, `group`, `use by=...`; SPEC.md:173, 178, 394), and placement on the worker nodes is the host's (SPEC.md:400-404).
4. **Deterministic Packaging & Replay (not built; run locks with replay already existed):**
   There is no `sympkg`, and the repository has no CI configuration.
   - **Locks:** a complete run can be locked into `run.lock.json`. The lock pins the program's SHA-256, the inputs and options, the source and SHA-256 of every imported module, the kernel identity and every recorded call.
   - **Replay** serves the recorded replies through an applicator that refuses every call, so it makes no model call (`symblic/kernel/lockfile.py:1-15, 140-145, 182-188`; SPEC.md:478-486, 555). Only replay is offline: a new run needs its models.
   - **Versions:** library modules have no version numbers, and `units@2.2.0` and `variational@2.2.0` do not exist. Modules are pinned by source hash. The variational adapter's version is 1 (`symblic/adapters/variational.py:18`), and it is recorded in the kernel identity.
   - **What determinism covers:** the kernel's own computation and the replay of recorded replies, not fresh model outputs. The kernel produced the same corpus hash on 27 profiles across three hosts. That is a tested equality, not a proof for every program (RESULTS.md:132-140).
5. **WebAssembly (WASM) Playground (not built, not attempted):**
   The proposal is to compile the kernel to WASM and run it in the browser. Before any claim, its startup, memory, portability and compatibility would have to be measured (RESEARCH-ADOPTION.md:123), for example against the 27-profile conformance corpus (RESULTS.md:132-140). Today the page runs programs through the operator-only API (SPEC.md:526-535).
