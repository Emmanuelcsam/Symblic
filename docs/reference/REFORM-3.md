## Objective and revised foundation

Preserve the original objective: people express small, explicit statements; models perform the difficult construction work; accepted results compose into programs and larger agent networks. Existing deterministic computation, code generation, mathematical adapters, empirical judgment and authorized effects remain available.

Revise one premise: statement precision alone does not guarantee perfect or repeated model execution. A useful formal interface instead specifies the construction task, authoritative inputs, accepted witnesses, state transition, dependency evidence and unresolved outcomes. A model may fail to find an accepted result. A checked formal result may remain conditional on empirical premises.

The resulting system has three complementary lanes:

- **Direct deterministic execution** for computations the existing kernel or adapter already supports.
- **Model/human construction with independent checking** for proofs, code, source witnesses and other artifacts with reusable acceptance procedures.
- **Empirical proposals with explicit uncertainty** where no complete formal checker of intended meaning is available.

The second lane addresses “moving all the programming into the kernel.” The kernel checks general inference rules or supplied obligations; it does not need to contain each proof or generate the target program. The first lane remains an efficient option, and the third preserves capabilities whose uncertainty cannot honestly be eliminated.

## Integration contracts

### Model construction stays separate from authority

A certificate cannot replace caller premises, the goal or a source contract. A model proposal cannot create an operator statement by setting an `origin` field. The host assigns provenance, associates trusted checker receipts with exact subjects, and carries the existing source/kernel/module/capability pins into execution.

The first proof fragment treats quoted human sentences as atoms. The model produces natural-deduction terms; the checker validates them. The epistemic policy and the logic are separate: the policy may withhold contested premises from actions even though a chosen formal calculus permits derivations from inconsistent assumptions.

### Evidence must be operational

Binding metadata, capsules, graph messages, retry snapshots, reports and replay must preserve the same dependency identities. Imported notebook claims stay bound to their historical run snapshot; later operator revisions are explicit new premises, not silent changes to the executed record. Receipt scopes include schema, encoded predicate, formal derivation, exact source relationship and finite examples; none upgrades empirical premises to truth.

In the installed 5 October runtime, imported facts and rules are conditional operator premises
bound to the module key, exact source hash and canonical predicate namespace.
An executed query selects declarations through its predicate and transitive rule
inputs. A successful retrying check can add a separate acceptance derivation when
an imported premise helped select the answer, including through an intermediate
Boolean or memoized value. The original proposal and check receipt stay immutable;
the trace links them to the refined binding. Retry restores the original snapshot,
and replay uses the retained module source. This is conservative dependency
provenance: static named-binding/default reads can retain unused parents, and a
predicate's full declaration set is not a minimal proof tree.

The RC2 runner preserves contested vote status, propagates unavailable support and detects missing or mismatched dependency references. Generated claims begin at revision 1 without withdrawal; runtime assessment records contain empty disagreement lists. Retry rollback removes rejected claims from the active report registry while retaining the attempt trace. These mechanisms must not be described as a persistent revision/withdrawal interface.

The standalone `symblic.kernel.epistemic.evaluate` and `context_manifest` APIs additionally process caller-supplied revisions, withdrawals and explicit disagreements. They are not called by the RC2 runner as a persistent claim workflow. The installed notebook uses them to assess imported snapshots and operator revisions. It retains original records, disagreement history and reasons for unavailable support. Import records bind source/report/metadata hashes and execution identity, and validate execution pins when present; these are local integrity records, not authenticated empirical truth. Operator content revisions clear earlier checks, and dependent claims retain their original references until rebuilt. Context export requires the displayed current head, closes selected dependencies and refuses unavailable support while explicitly identifying any hash-only values. No notebook edit changes an already executed run.

The notebook's 32 Python tests and two browser journeys verify these scoped operations with temporary stores and intercepted HTTP, including uncertain-create retry and stale-edit recovery. These remain component checks; installation is recorded in the 5 October release above. A disagreement is not automatically a refutation, and a refuted premise does not automatically make every dependent statement false. Multiple model readings of a shared source remain proposals with acquisition independence unassessed.

### Context is a declared input contract

Build fixed prompt parts before packing dependencies. Count the system instructions, exact statement, definitions, examples, feedback and answer format/schema in the chosen budget unit. Required selected values must be provided or packing fails. Ancestor identities and support conditions remain lineage metadata; the runtime does not automatically expand forgotten or unrequested ancestor raw values into the prompt. The standalone manifest helper can close explicit required record dependencies when the caller supplies those records. Any optional omission lists the exact identity and reason. Rewrites or summarization may produce additional proposed claims, but cannot silently replace required source evidence.

### Networks use existing execution and fleet boundaries

A node has declared inputs/outputs, effect class, evidence requirements, state and budget. An edge has a type and explicit evidence-transfer rule. Cycles require a bounded feedback schedule; arrival order must not silently determine the accepted value. Durable execution needs attempt identities, recovery states and original outcomes before provider/effect redispatch.

Use registered admitted launch paths and existing provider/effect adapters. New graph syntax must not create a hidden shell or independent authority system. More nodes add suitable capacity; they do not combine RAM or establish independent beliefs by themselves.

The operator graph API in RC2 connects this contract to the existing private jobs and Graphs interface. It admits native verified sources, concrete routes, schemas and output bindings before launching. The web lane accepts effect-free graphs; explicitly injected Python hosts retain the supported effects lane. Graph execution is sequential, with separate pessimistic reservations and actual issued-call journals.

Graph and policy jobs share durable launch generations. Stop records cancellation before waiting for the worker. Duplicate pending resumes do not relaunch during startup grace, and a stale worker cannot start or finish a newer generation. Confirmed inactive interrupted stops expose Resume while preserving the old cancellation marker. Unknown provider/effect outcomes remain unresolved; generation control does not make an external action exactly once.

List views report recorded status. Opening terminal graph receipts uses a no-dispatch native audit. Policy views and selection export check implementation/host identities and underlying graph outcomes; selection audits training only, while evaluated views can audit heldout evidence. Drift or corruption removes current assurance rather than silently rerunning a model. See [AGENT-GRAPHS](AGENT-GRAPHS.md) and [POLICY-EXPERIMENTS](POLICY-EXPERIMENTS.md) for exact boundaries.

### Learning changes a candidate, then earns adoption

Routing, prompts, decomposition and topology can be candidate parameters. Define a task-success objective with cost and regression constraints, retain development/held-out separation, record every attempted configuration and measure shared failures. Textual feedback, search and policy-gradient estimation are distinct possible update mechanisms. The initial graph runtime does not become a trained neural network simply by connecting models.

The implemented policy lane selects among explicitly supplied finite routing candidates under frozen exact-output fixtures and a declared objective. It records every planned assignment and issued provider call; heldout comparison cannot change the selected policy. Copying a selection into a future graph draft is an explicit operator action that invalidates that draft's prior check. Ongoing runs retain their frozen policies. Prompt/topology optimization and statistical evidence of general improvement remain separate work.

## Evaluation needed before stronger claims

Use paired task families and matched information/checker budgets. At minimum compare direct prompting, typed output, matched retries, ordinary deterministic-tool use, witness-producing construction and graph composition. Report small-model-only and assisted outcomes separately.

For every condition retain the original request, authoritative assumptions, source versions, available examples, hidden tests, provider/model identities, repair exposure and all planned case outcomes. Compare task success and false acceptance, not only accepted-result agreement. Include refusal, timeouts, latency, compute, token/call cost and human specification/debugging effort.
